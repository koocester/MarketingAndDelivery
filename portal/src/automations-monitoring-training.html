Automationsand monitoring

How the machine watches itself, and how you keep it honest.

Your mission

Know how the machine watches itself.

Dozens of automations run the company while everyone sleeps. Your job is to know when one goes quiet, trust the alerts that reach you, and act before anything reaches a client.

The one rule

Silence means healthy.

A good monitor is quiet. You should hear nothing when all is well, and a clear message the moment something truly changes. If you are being pinged all day, the monitor is broken, not the system.

What success looks like
You are winning when…
Everything is greensystems up, workflows live, no red states

Part one

The automation stack

Two engines run the work.

Two engines

n8n and Lark do the running.

n8n workflows

  • The heavy engines
  • Dashboards, briefs, reports
  • Syncs to Supabase and Metabase
  • Content engine, leaderboards
  • Event driven and scheduled

Lark Base automations

  • Live inside each base
  • Buttons that move stages
  • Scheduled scans and digests
  • Notifications to Updates channels
  • Auto assign and fan out
Why it matters for monitoring

Only one of them has an open door.

n8n exposes an API, so we can read every workflow and every failed run from the outside. Lark automations do not, so we watch them a different way. Know which engine a job lives on before you go looking for it.

Part two

The three layers of monitoring

Three failure modes, three tools.

The whole model on one screen
LayerCatchesTells you
Error HandlerAny workflow that runs and errorsTech Updates, instantly
WatchdogA site or system going downTech Updates, on change only
HealthchecksThe watchdog itself dyingEmail, if it goes silent

Three layers, because no single tool catches all three failure modes.

Layer one · failures

The Error Handler catches every crash.

One n8n error workflow listens across all workflows. The moment any workflow errors, it posts to the Tech Updates group. It is event driven, so it costs nothing until something breaks. A repeat from the same workflow is muted for an hour so a single fault cannot spam you.

Layer two · outages

The Watchdog checks, and stays quiet.

Every twenty minutes the watchdog pings the portal, the sign in, the dashboards and the site. It only messages you when a state changes, once when something goes down and once when it recovers. Checking often is cheap. Messaging often is not, so it does not.

Layer three · the monitor itself

Healthchecks watches the watchdog.

The watchdog pings an outside service on every healthy run. If those pings stop, that service emails the team. It lives outside our own n8n, so it catches the one thing the watchdog never could, its own death. This is the answer to who watches the watchdog.

Why three and not one
Each layer covers a blind spot.

The Error Handler cannot see a workflow that never ran. The Watchdog cannot see itself die. Healthchecks cannot read a single failed run. Stacked together, nothing slips between them.

Part three

Lark's own quota guard

A different kind of alarm.

Lark admin · usage alerts

Lark warns you about volume.

In Lark admin there is a usage alerts and auto deactivation page. It watches how many times automations run, warns when the count climbs, and switches off any single automation that runs away. It also tracks the monthly run quota. Keep it on. It protects your bill.

Do not confuse the two

Volume is not failure.

Quota guard (Lark)

  • Answers, is it running too much
  • Catches runaway loops
  • Protects the monthly quota
  • Auto deactivates the offender

Health monitoring (ours)

  • Answers, did it fail or stop
  • Catches crashes and outages
  • Catches silent death
  • Alerts a human to act

A workflow can be perfectly quiet and completely dead. Only our health layers catch that.

Part five

When you get an alert

A calm order of moves.

The alert playbook

Read, confirm, then fix.

01 · ReadName the failure

Identify the workflow, system and reported error.

02 · OpenGo to the exact run

Use the alert link; do not inspect a different instance.

03 · ConfirmCheck it is still real

A single blip may already have self-recovered.

04 · DiagnoseRead the failed node

Follow the evidence and find the cause. Never guess.

05 · Fix & rerunChange the smallest part

Rerun it and watch the result pass before closing.

06 · EscalateStop at structural risk

Money, access, client impact or system design goes to your manager or Hakim.

Where the truth lives

The system documents itself.

1Alert linkThe exact incident and affected run.
2Execution / health checkThe evidence: node output, error and current system state.
3Tech BaseThe owner, priority, status and operational record.
4Training & change logThe expected design and what changed.
Password Vault only for credentials. Never paste secrets into chat. Structural risk → your manager or Hakim.
