Part one

n8n versus Lark

Two automation layers. Know which does what.

Two layers, two jobs

Native Lark automations

react inside the base
  • Fire when a record changes
  • Move stages, notify a channel, stamp a field
  • Live and die inside one base

n8n

the always-on layer
  • Runs 24/7 on its own timetable
  • Reaches across systems — Lark, Supabase, Metabase and more
  • Has its own Lark token, so it never needs a person signed in
The line: native Lark automations react inside the base. n8n reaches across systems and runs on a schedule. When work must happen at a set time, or must touch more than one system, it belongs in n8n.
What lives in n8n
Three things run here, on a clock.
JobWhat it does
Scheduled briefsThe daily Chief Executive Officer brief and the manager brief, built and sent every morning.
Data syncsFollower counts and content metrics pulled in on a schedule and written to the database.

Because n8n runs on its own connection, none of these depend on a person being online.

The daily briefs

Built and sent from n8n, not from a laptop.

Two briefs go out every morning: a Chief Executive Officer brief and a manager brief. Both are assembled and delivered inside n8n — so they land whether or not anyone is at their desk. There is no operator pressing send.

Why it matters: a brief that depends on someone being online is a brief that gets missed. Move it to the always-on layer and the morning takes care of itself.
Part two

The feedback loop

Where performance data goes, and how it stays honest.

Where the numbers live

Data to Supabase. Dashboards in Metabase. Not Lark.

Posted content → Supabase · the database → Metabase · the dashboards

Content performance flows into Supabase, the database. The dashboards are built in Metabase — never in Lark. When someone asks for a chart, that is where it is built.

How a video meets its numbers
The post URL is the join key.

Performance data doesn't know which video it belongs to on its own. The post-URL fields are what connect a video record to its performance — they are the join keys that tie the two sides together. Keep them clean, and the loop closes automatically.

The rule that protects history

Append dated rows. Never overwrite.

When you sync followers or metrics, add a new dated row each time. Overwrite the current value and you lose the trend — there is no way to draw a line you never recorded. History only exists if you keep every reading.

Watch out: the live followers sync replaces the current number and keeps no history. Never build a trend off the live value — append instead, or the chart has nothing to plot.
Part three

Integration hygiene

Secrets, and watching for silent failure.

Credentials · handle with care

Store secrets as credentials. Never inline.

  • Store every key as a credential or secret — never hard-code it inline in a node or a workflow.
  • If hard-coding is temporarily unavoidable — stage the value only in the company Password Vault, never a local file or personal drive, then remove it once the credential is working.
  • An inline API key is a live risk — anyone who can open the workflow can read it.
  • Rotate any secret that has been exposed — the moment a key leaks, replace it. A rotated key is worthless to whoever saw the old one.
Real risk: hard-coded secrets have been found inline in these workflows. If you spot one, move it to a credential and rotate it — do not leave it sitting in plain text.
Watch the runs
A silent failure is worse than a loud one.

Watch the execution history. A workflow that errors loudly tells you it broke. A workflow that fails silently — a brief that never sent, a sync that skipped a day — costs you far more, because nobody knows until the damage is done. Check the runs before you trust them.

Part four

Changing things safely

Three moves that keep you out of trouble.

Safe change · published means live

Take it down before you touch it.

Published→ Take down→ Troubleshoot→ Test→ Republish

A published automation is production. Do not edit its nodes, mappings, credentials or schedule while it is live. Take it down first, troubleshoot safely, prove the result, then publish it again.

Protect the operation: if taking it down interrupts a critical workflow, agree the maintenance window before you touch it.
Safe change · the sequence

Take down. Duplicate. Test one. Confirm downstream.

1 · Take down → 2 · Duplicate → 3 · Test one → 4 · Confirm downstream
  1. Take a published workflow down first — never troubleshoot by editing production in place.
  2. Duplicate before you edit — keep the working version intact so you can fall back.
  3. Test with a single execution — one run, watched end to end, before it goes on the clock.
  4. Confirm the downstream system received it — check Lark, Supabase or the channel actually got what you expected. A green run is not proof the other side arrived.
