How to read, safely change, and rebuild the fan-outs that run the Marketing & Delivery base.

Your mission

Records move through stages and create linked records on their own. Your job is to understand exactly how, change it when it needs changing, and never ship a fix that runs twice or does nothing at all.

Lark Base holds the records. Native Lark automations push them through stages. AnyCross is the fan-out engine that creates the linked records automatically — one source record spawns the ones that depend on it.

What a fan-out is
One record enters. Many are born.

A fan-out is an automation that reacts to one record reaching a state and creates a set of linked records from it — the downstream work it implies. That is the engine you are looking after. Understand it before you touch it.

Part two

The golden rule

Understand before you change.

Golden rule · read the whole automation

Scroll to the very bottom before you judge it.

An automation is a stack of action steps. The summary caption at the top undercounts them — it never shows the whole story. Open the action panel and scroll all the way down to "Add action". Only when you have seen every step do you know what it actually does.

The trap: you read the caption, assume you understand, and edit blind. The step that bites you is the one you never scrolled to.
Part three

Idempotency

Run it once, run it twice — same result.

Idempotency · guard against double-runs
A fan-out that runs twice makes duplicates.

The same trigger can fire more than once. If the automation has no guard, it spawns the linked records again — and now the base has doubles nobody asked for. Every fan-out you build or change must be safe to run twice.

How to make it safe · the "already done" test

Ask a fact that can't lag.

Trust this →

  • A link count — "does this record already have its children?"
  • A helper flag field you set the instant the work is done
  • An only-when-empty guard — create only if nothing's there yet

Don't trust this ✕

  • A rollup that can lag behind the write that fed it
  • A number that's "usually" updated by now
  • Any signal that is eventually right but not right yet

Derive "already done" from something the record itself knows right now — a link count or a flag — never from a value that updates a beat late.

The guard in one line
Create only when the slot is empty.

Wrap every "create linked record" step in a condition: only run if that link is still empty. Now a re-run finds the work already there, does nothing, and moves on. That single guard is what makes the whole fan-out idempotent.

Part four

Triggers & buttons

What starts an automation — and its hidden edges.

Triggers · pick the right one

"Matches conditions" fires on entry only.

Matches conditions

edge-triggered
  • Fires only when a record enters the state
  • Ignores writes made by the Application Programming Interface (API)
  • Great for a one-time "on arrival" fan-out

When a record updates

watches a field
  • Fires every time the watched field changes
  • Use this to react to a field changing
  • The right choice when a value can change more than once
The mistake: wiring "matches conditions" and expecting it to fire when a field later changes, or when the API writes the value. It won't. To react to a change, watch the field with "when a record updates".
Buttons · one button, one automation
A button binds to exactly one automation.

A button doesn't branch. It fires a single automation. If you need different outcomes, don't fork on the button — fork on the data after the click, inside that one automation's conditions.

Buttons · the silent no-op

A click can do nothing, and leave no log.

Every automation has a conditions block. If a click doesn't meet those conditions, the automation no-ops silently — no action, no run in the log, no error. The user swears they clicked; nothing moved.

Check two places first. Read the conditions block, then inspect the first instance of each automation node. The earliest node is usually where a wrong condition, mapping or input catches you.
Buttons · duplication corrupts them

Don't duplicate an automation to reuse it.

A duplicated automation can carry a corrupted card button that quietly blocks activation — it looks fine but won't turn on. If you hit that, turn OFF the "Add buttons" option to activate, then rewire the button cleanly. Better: edit the original in place instead of duplicating.

Records · where they're born
Every record is born at the first real stage.

Records enter at the first stage — Not Started, or Planning — never dropped into the middle of the flow. So don't wire a fan-out to fork on which button was pressed. Let the record be born clean, then fork on the data it carries.

Part five

Change it safely

The moves that keep you out of trouble.

The safe-change loop

One record. Watch the log. Then scale.

  1. Read the whole automation — scroll to "Add action" before you touch a step.
  2. Test on one record — never on hundreds, never on live client work.
  3. Watch the run log — confirm it fired, and did only what you expected.
  4. Keep automations OFF during a migration — a mass import must not trip live fan-outs.
  5. Re-enable at a known checkpoint — turn them back on together, at an agreed moment, not one at a time in the dark.
Escalate anything structural to Hakim. Small, tested, reversible changes are yours. Reshaping the flow is a conversation first.
